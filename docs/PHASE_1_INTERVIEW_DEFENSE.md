# Phase 1 interview defense and handover

This is a guide to **what the repository executed**, using the authoritative `data/raw/Case_Study_1_Install_Base_Reactivation.csv` and the fixed default analysis date **2026-10-09**. It is not a claim that the CSV describes a representative real-world install base. The figures below come from locally regenerated [metrics.json](../outputs/phase1/metrics.json), the named CSV outputs, and the executed [notebook](../notebooks/01_data_foundation.ipynb). Account-level, parent-level, and reconstructable date outputs are excluded from Git but retained locally; the code recreates them from the separately supplied source. Run `python -m everpure_case.source_integrity --repo-root .` to verify the approved source baseline, then `everpure-phase1 --repo-root . --as-of 2026-10-09` from the repository root.

## 1. What runs, in order

1. [config.py](../src/everpure_case/config.py) fixes the 12-column `SOURCE_COLUMNS` contract, `DEFAULT_AS_OF`, relative file paths, and the closed `REGION_MAP`.
2. [ingestion.py](../src/everpure_case/ingestion.py), `read_source`, reads every CSV column as text with `keep_default_na=False`, checks the **exact column order**, and adds `source_row_number` (CSV header is line 1). Thus an empty string and literal `nan` remain distinguishable, and account IDs cannot be coerced into numbers. A changed schema raises `SchemaError`.
3. [quality.py](../src/everpure_case/quality.py), `normalize_region` and `clean_accounts`, append parsed dates, finite numeric fields, three-state partner ownership, valid ticket counts, two inactivity definitions, explicit four-state comparison status, and field-level exceptions. `calendar_2y_proxy` is reused by `analysis_date_sensitivity`; `eligibility_reconciliation` cross-tabulates the two known/unknown views without deciding which source is correct.
4. [hierarchy.py](../src/everpure_case/hierarchy.py), `resolve_hierarchy`, traces each parent link to a root and records missing parents, self-links, duplicate-ID ambiguity, and cycles. `parent_summary` joins the mapping back by `source_row_number` with `validate="one_to_one"`, then sums each resolved account row once.
5. [sql_analysis.py](../src/everpure_case/sql_analysis.py), `run_queries`, registers cleaned `accounts` and `hierarchy` DataFrames with in-memory DuckDB and executes four current-data SQL files. The hierarchy SQL is executed separately in `run_pipeline`. The longitudinal template remains an unexecuted interface for **real** future account-period data.
6. [pipeline.py](../src/everpure_case/pipeline.py), `run_pipeline`, orchestrates the real-data steps; preserves original columns and row count; reconciles raw, root, and region spend to cents; and writes deterministic files to [outputs/phase1](../outputs/phase1/). `main` exposes `--repo-root` and `--as-of`. [build_notebook.py](../scripts/build_notebook.py) creates the notebook; [verify_notebook.py](../scripts/verify_notebook.py) executes it in a fresh kernel and saves results.
7. [synthetic_demo.py](../src/everpure_case/synthetic_demo.py), `validate_fiscal_calendar`, `execute_synthetic_demo`, and `run_synthetic_demo`, reject incomplete or misordered fiscal calendars, validate invented hierarchy/revenue fixtures, execute separate account and root decay SQL, and write only to [synthetic_demo outputs](../outputs/phase1/synthetic_demo/). Nothing from these fixtures enters real accounts or financial totals.
8. [source_integrity.py](../src/everpure_case/source_integrity.py), `verify_authoritative_source`, is a separate approved-baseline gate for the CSV's SHA-256, exact row count, and Decimal spend sum. Phase 2 must run it before using this source; the generic pipeline remains available to isolated mutation tests.

The [tests](../tests/) include deliberately synthetic *test fixtures* for duplicate IDs, missing parents, self-links, cycles, multi-level roots, cutoff dates, and SQL windows. Those fixture values are never mixed with the case-study outputs. The actual file has **2,000 rows, 2,000 unique IDs, 301 roots, 1,699 children, and no unresolved hierarchy paths**.

Exception rows are **not** distinct accounts; one account can have several issues. No default deduplication or deletion changes the spend denominator. |
| Normalize only the documented region variants using trimmed whitespace and case folding. | Six raw labels become five canonical labels. Otherwise France would be split across two commercial reports. This does not establish how mixed-region parent groups should be assigned. |
| Accept only `Green`, `Yellow`, `Red` as known SFDC health. | **444** literal `nan` and **400** literal `Missing` values yield **844** unknowns. | Treating unknown as Green would understate review needs; treating it as Red would fabricate risk. Health is not an observed reactivation outcome. |
| Keep partner `1`, `0`, and unknown separate. | **654** missing partner flags; **236 of 301** root groups mix known partner values. | Ownership should not be guessed before partner or direct-sales execution. Mixed child flags may reflect legitimate arrangements; a conflict flag calls for review. |
| Exclude ticket value `999` from valid ticket-count statistics, retaining raw code and `ticket_sentinel`. | **322** rows have 999, whereas other observed counts are 0, 1, 2, 3, or 5; **324** genuine zeros remain zero. | The case identifies 999 as a sentinel and its separation from ordinary counts supports that rule. Turning 999 into zero would misstate service load. There are no ticket timestamps, so no ticket **velocity** is calculated. |
| Validate dates with explicit `YYYY-MM-DD` parsing; validate finite, nonnegative spend and usage and discount fraction range 0–1. | No invalid dates, non-finite numeric values, negative spend, or out-of-range discounts were found in the real file. Discounts span 0.05–0.65. | `0.25` is interpreted as a 25% fraction for validation, not proof of an approved commercial discount or future scenario. Missing discount is flagged once, separately from out-of-range values. |
| Compare source-reported inactivity with a date-derived proxy; flag a gap of at least 0.5 approximate years. | **1,546** known rows exceed that review threshold; **562** also disagree on two-year eligibility. | The six-month threshold is an explicit *review rule*, not a correction or statistical estimate. Both source and date-derived values are retained. The measurement date of `years_inactive` is unknown. |

The business definition says **two fiscal years**. `calendar_2y_proxy_eligible` instead compares last booking with **2024-10-09**, exactly two calendar years before the configured date. `reported_2y_eligible` uses `years_inactive >= 2`. [inactivity_reconciliation.csv](../outputs/phase1/inactivity_reconciliation.csv) reports **1,144 source eligible, 562 source ineligible, and 294 source unknown**, while all 2,000 are calendar-proxy eligible. `eligibility_comparison_status` accordingly has 1,144 `agree_eligible`, 562 `disagree`, 294 `unknown`, and zero `agree_ineligible`. `eligibility_disagrees=False` includes the 294 unknown comparisons; it cannot be treated as agreement. Neither view is silently promoted to confirmed fiscal eligibility.

For inactivity exceptions, the revised locally generated [register](../outputs/phase1/data_quality_exceptions.csv) leaves `cleaned_value` empty and puts the independently calculated calendar-years reference in `comparison_value`. Across the source, **1,546** known rows exceed the six-month review threshold. The reference is a comparison, **not** a replacement for reported inactivity.

## 4. How hierarchy resolution works: a worked test fixture

`resolve_hierarchy` trims keys for lookup, counts duplicate IDs as ambiguous, then recursively follows each parent pointer until it reaches an empty parent (root). A `seen` set detects a cycle. A memo stores completed paths; `hierarchy_status` and `hierarchy_depth` make failures and depth explicit. On this source the maximum depth is **1**, although [test_hierarchy.py](../tests/test_hierarchy.py) verifies a two-level child path and unresolved cases. Python's recursion limit bounds pathological depth; the resolver is not unbounded.

The deliberately invented three-row fixture in [test_hierarchy.py](../tests/test_hierarchy.py) exercises a deeper path than the actual source:

| Invented account | Immediate parent | Resolved root | Depth | Fixture spend (USD) |
|---|---|---|---:|---:|
| `A` | empty | `A` | 0 | 10 |
| `B` | `A` | `A` | 1 | 20 |
| `C` | `B` | `A` | 2 | 30 |

`resolve_hierarchy` follows `C` to `B` to `A`; `parent_summary` yields **3 account rows, 1 direct child of root A, and 60 fixture dollars**. The separate [direct_child_counts.csv](../outputs/phase1/direct_child_counts.csv) counts immediate parent references independently of root grouping. In the actual source, there are **301 roots, 1,699 children, and maximum depth 1**; the [locally generated mapping](../outputs/phase1/account_hierarchy.csv) holds the account-level detail. Its group sums are *recorded exposure proxies*: if a parent source amount already includes child amounts, additive totals could double count economic revenue. The source supplies no consolidation rule.

The one-to-one join on `source_row_number` prevents a duplicated account row from multiplying spend through a parent join. The pipeline checks **$2,541,024,291 raw = $2,541,024,291 resolved group spend + $0 unresolved**, and SQL regional and root sums match that same source-row total. This proves arithmetic coverage, **not** economic consolidation.

The [parent-child spend comparison](../outputs/phase1/parent_child_spend_comparison.csv) adds an important check: **291 of 298** referenced parents have less recorded spend in the parent row than the sum of their direct children's rows. That contradicts a *simple full-child-inclusion* story when amounts have the same basis. It still does not tell us the true periods, partial inclusion, or consolidation conventions. Source-row additive spend, possible economic consolidated revenue, and evidence against one simple inclusion rule remain separate claims.

## 5. CTEs and windows: tested input → output

In [window_analytics.sql](../sql/window_analytics.sql), `booked` assembles one dated row per resolved account, then `neighbors` partitions by `root_account_id` and orders by `booking_date, account_id`. The invented fixture in [test_sql.py](../tests/test_sql.py) produces:

| Invented account | Booking date | `LAG` previous account date | `LEAD` next account date | Days since previous | Days until next | Recency `DENSE_RANK` |
|---|---|---|---|---:|---:|---:|
| `A` | 2020-01-01 | null | 2020-01-05 | null | 4 | 3 |
| `B` | 2020-01-05 | 2020-01-01 | 2020-01-09 | 4 | 4 | 2 |
| `C` | 2020-01-09 | 2020-01-05 | null | 4 | null | 1 |

For the middle fixture row, `LAG` takes 2020-01-01, `LEAD` takes 2020-01-09, and `date_diff('day', ...)` yields 4 days in each direction. `DENSE_RANK` orders the latest date first, so `C` is rank 1. These are adjacent **accounts' single last-booking dates**, not successive bookings of one account. In the actual source, every booking date follows an exact numeric-account-ID sequence; within-root date gaps therefore mirror ID gaps. The [locally generated window output](../outputs/phase1/window_analytics.csv) is a source-pattern diagnostic, not independent customer behavior or revenue decay. Null at an edge means no adjacent account in that direction. The separate non-monotonic fixture in `test_sql.py` ensures an incorrect switch to ID ordering would fail.

The same SQL test fixture demonstrates two other CTE paths. [spend_concentration.sql](../sql/spend_concentration.sql) sums the invented 10 + 20 + 30 = **60** in `root_spend`; [account_opportunity.sql](../sql/account_opportunity.sql) ranks fixture accounts by spend within root as `C` = 1, `B` = 2, `A` = 3. `DENSE_RANK` would give tied values the same rank without leaving a gap; this fixture has no ties. For the actual source, [regional_spend.sql](../sql/regional_spend.sql) gives France rank 1 with **$845,049,984 / $2,541,024,291 = 33.256%**. Root and region calculations use different grouping definitions; neither should be added to the other. The actual **0.881** correlation of root count and additive spend means large groups naturally rise in total-spend rankings; account-level and root-level financial tables are local-only.

### Executed longitudinal example — separate invented data

**SYNTHETIC METHODOLOGY DEMONSTRATION — NOT OBSERVED EVERPURE REVENUE.** The invented [fixture](../data/synthetic/account_period_revenue.csv) has five accounts, two roots, and four indexed fiscal periods; [synthetic_demo.py](../src/everpure_case/synthetic_demo.py) validates its mapping and executes [synthetic_account_decay.sql](../sql/synthetic_account_decay.sql) and [synthetic_root_decay.sql](../sql/synthetic_root_decay.sql). The actual [account output](../outputs/phase1/synthetic_demo/synthetic_account_decay.csv) for `SYN_A` period 2 is prior **$100**, current **$80**, elapsed **1** period: absolute change **-$20**, consecutive percentage **(80 - 100) / 100 = -20%**, signed velocity **(80 - 100) / 1 = -$20 per fiscal period**. `LAG` retrieves 100, `LEAD` shows the next observed 60, and `DENSE_RANK` orders period 4 as the newest observation.

`SYN_B` has **no record** for period 3: period 2 $50 to period 4 $70 gives an across-observation +$20, **two** elapsed periods, and +$10 per period, but **null ordinary quarter-over-quarter percentage** with status `nonconsecutive_gap`. `SYN_C` has a **real zero** in period 1: its period-2 move from $0 to $20 keeps +$20 absolute change while percentage is null (`consecutive_zero_baseline`), never infinity. At root `SYN_R1`, period 2 is a complete **$130** versus period 1 **$150**, so change is -$20, -13.3333%, and -$20 per period. Period 3 has only two of three member observations: $60 is labeled a **partial sum**, complete root revenue is null, and period-4 ordinary quarter-over-quarter change is suppressed. The synthetic root-only assumption is that parent own revenue excludes its children; it is **not** carried over to Everpure historical spend. Full formulas and expected rows are in [the demonstration guide](SYNTHETIC_REVENUE_DEMO.md).

## 7. What this file cannot establish

- **True two-fiscal-year dormancy or install-base prevalence.** The fiscal-year boundary, precise business cutoff, and broader install-base denominator are absent. The business brief's “over 50%” is not estimable from these 2,000 supplied rows.
- **Revenue decay or CAGR.** One `historical_spend_usd` number per account has no account-period sequence or declared spend period. Differences between two children cannot stand in for within-account revenue change.
- **Empirical reactivation probability or a Cox model.** There are no observed reactivation labels, event dates, observation windows, or censoring information.
- **Ticket velocity.** `open_support_tickets` is one undated stock count per account; no timestamped ticket events or observation duration exist.
- **Verified consolidated revenue, ARR, or recoverable NPV.** The source lacks parent-child consolidation rules, spend measurement period, gross margin, campaign cost, renewal horizon, and approved discount and financial-rate assumptions.
- **An actual GTM route.** Partner ownership is unresolved for 654 accounts, and fiscal eligibility and ticket velocity are unverified. [account_opportunity.csv](../outputs/phase1/account_opportunity.csv) is a descriptive feature table only.

The [analysis-date sensitivity output](../outputs/phase1/analysis_date_sensitivity.csv) shows **1,269** calendar-proxy eligible at 2024-06-22, **1,634** at 2025-06-22, and **2,000** at 2026-06-22 and 2026-10-09. The source-reported inactivity field may refer to an unknown earlier snapshot. That possibility cannot be verified without provenance, and a two-fiscal-year definition is not identical to a rolling two-calendar-year cutoff. The brief's “over 50%” cannot be validated without the full install-base denominator.

`has_manual_review_exceptions` in [account_quality_summary.csv](../outputs/phase1/account_quality_summary.csv) is a quality-triage flag, with `needs_manual_review` retained as an alias. False means no issue was *classified* `manual_review`; it does **not** mean complete health, partner, tickets, inactivity, or confirmed fiscal eligibility. A future routing-readiness interface must fail closed on unknown required fields, unresolved hierarchy, or unconfirmed fiscal eligibility and record the blocking reason. No route or readiness decision is computed in Phase 1.

| 1. | 2. Keep health, partner ownership, and ticket sentinel as distinct unknown/error states. | Impute Green, infer a partner owner, or recode 999 to zero. | Those alternatives fabricate commercially consequential signals; 324 valid ticket zeros are observably different from 322 sentinels. |

## 9. Fifteen interviewer questions and model answers

1. **What is the grain?** One row per account ID in this CSV. `read_source` adds a source line number; 2,000 rows and 2,000 IDs were verified. Parent-group outputs are aggregations of those rows, not new account events.
2. **The brief says there are duplicates. Where did you deduplicate?** Nowhere: the actual file has **zero duplicate account IDs**. `clean_accounts` flags duplicates if a future file has them; `resolve_hierarchy` marks ambiguous keys unresolved instead of choosing a row arbitrarily.
3. **Why read numeric columns as strings first?** To preserve exact account IDs, empty strings, and literal `nan` while validating the schema. `clean_accounts` then parses numbers explicitly and records invalid values rather than letting import inference erase source distinctions.
4. **Why merge the two France labels?** They differ only in capitalization and trailing whitespace. `normalize_region` maps both to `EMEA - France`, yielding 667 accounts and $845,049,984; raw labels remain available for audit.
5. **Why is ticket 999 missing but ticket 0 valid?** The brief identifies 999 as a sentinel, and the actual non-sentinel values are 0, 1, 2, 3, and 5. `tickets_clean` masks 999 and retains the raw field and flag; there are 322 sentinels and 324 zeros.
6. **What explains the 2,000-versus-1,144 dormancy difference?** The first is a date-derived *calendar* proxy at 2026-10-09; the second uses source-reported `years_inactive >= 2`. `eligibility_comparison_status` identifies 562 known disagreements and 294 unknown comparisons, not 294 agreements. We cannot establish which input is authoritative.
7. **Why choose 2026-10-09 rather than today's date?** It is the specified Phase 1 date, stored in `DEFAULT_AS_OF` and exposed via `--as-of`. The same proxy yields 1,269 eligible on 2024-06-22, 1,634 on 2025-06-22, and 2,000 by 2026-06-22. The source `years_inactive` may reflect another snapshot, but its measurement date is unavailable.
8. **Can the case's fiscal-year definition be applied?** Not yet. We need the fiscal-year start, the exact interpretation of “past two fiscal years,” and trusted booking-date semantics. The repository deliberately reports a calendar proxy separately.
9. **How does the hierarchy code handle a cycle?** `resolve_hierarchy.walk` carries a `seen` set; revisiting a key returns `cycle` and no root. [test_hierarchy.py](../tests/test_hierarchy.py) checks `A → B → A`, plus missing and self-referencing parents. None occur in the supplied CSV.
10. **Why call the parent total a proxy?** `parent_summary` adds each account's recorded spend once, but the source never says whether a parent's amount already includes children. For 291 of 298 referenced parents, the parent row is below its direct-child sum, arguing against simple full inclusion on a common basis. That still cannot establish the actual accounting rule. The fixture's 60-dollar additive sum demonstrates the computation, not verified consolidated revenue.
11. **Why not allocate all child spend to the root's region?** The actual source has 294 multi-region roots. `regional_spend.sql` uses each row's own region and reconciles to source spend. A root-region allocation would impose an undocumented attribution rule.
12. **What exactly do `LAG` and `LEAD` measure?** In `window_analytics.sql`, they return previous and next *accounts'* single last-booking dates within a root. The invented `test_sql.py` fixture yields four-day adjacent gaps. In the actual source, these gaps follow the account-ID date pattern, so this is not customer purchase frequency or revenue decay. The separate synthetic decay SQL uses `LAG` on repeated fiscal periods *within one invented account*.
13. **What does `DENSE_RANK` add?** It orders root spend in `spend_concentration.sql`, region spend in `regional_spend.sql`, and within-group/region account values. In the invented `test_sql.py` fixture, within-root spend ranks are `C` = 1, `B` = 2, and `A` = 3; ties would share a rank.
14. **How did you guard against SQL join inflation?** Python merges hierarchy on unique `source_row_number` with `validate="one_to_one"`; SQL also joins on that key. `run_pipeline` reconciles raw, resolved-plus-unresolved, root SQL, and regional SQL amounts **to cents**, avoiding floating-point false failures but still detecting one-cent differences. The actual total stays $2,541,024,291.
15. **How can I reproduce and check this?** Install `.[dev]`, run `everpure-phase1 --repo-root . --as-of 2026-10-09`, `python -m everpure_case.synthetic_demo --repo-root .`, pytest, Ruff, and `python scripts/verify_notebook.py` as in the [README](../README.md). Adversarial pipeline tests use isolated repository copies so they cannot overwrite the approved real-data artifacts. Inspect the labeled synthetic output and the real [metrics](../outputs/phase1/metrics.json) separately.

## 10. Five hostile questions and candid answers

1. **“You claim every account is dormant, while the business says only over half. Did you manufacture eligibility?”** No. The claim is strictly that all 2,000 *supplied rows* have last-booking dates on or before a two-calendar-year cutoff. The file lacks the full install-base denominator and the fiscal calendar. I would not call the 2,000 fiscally dormant or estimate enterprise prevalence from this extract.
2. **“Isn't your $2.54 billion figure just double-counted parent and child revenue?”** It is the sum of the 2,000 *recorded values*. The code ensures each CSV row appears once, but that does not establish economic consolidation. Parent amounts are below direct-child sums for 291 of 298 referenced parents, which weakens *simple full-child inclusion*, not every possible overlap. I require accounting rules before treating the total as consolidated revenue or NPV input.
3. **“These dates are obviously fabricated. Why analyze booking recency at all?”** Booking dates increase exactly with numeric account ID, and contract start is 365 days earlier. Within-root ranks and gaps collapse to ID arithmetic. I retain the SQL as an explicitly labeled source-pattern diagnostic with a non-monotonic ordering regression test, not as a customer-behavior measure or model feature.
4. **“You used `LAG` and `LEAD` to pretend you calculated Everpure revenue decay, didn't you?”** No. The real-data window compares different accounts' single last-booking dates. A separate, labeled synthetic fixture executes account-period and root-period decay SQL with missing-period and zero-baseline controls. Its invented values never enter the real totals. Empirical Everpure decay remains unidentifiable from this CSV.
5. **“Unknown accounts pass your `needs_manual_review=False` flag, so isn't the dataset ready for routing?”** No. That flag means only that no exception was classified for manual review. `eligibility_comparison_status='unknown'` remains unknown, and health, partner, or ticket fields may also be unresolved.
